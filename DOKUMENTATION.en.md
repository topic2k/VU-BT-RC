## Overview

![VU+ HID Raw Remote](logo.docs.png)

This integration reads the VU+ BLE remote directly through Linux `evdev` and
exposes it as a Home Assistant device.

Linux reports several special VU+ buttons as `KEY_UNKNOWN = 240`. Their underlying
`MSC_SCAN` values still distinguish them. The integration uses regular Linux
keycodes for standard buttons and `MSC_SCAN`/HID usage for these consumer buttons.

## Requirements and permissions

- Home Assistant **2026.9.0** or newer. The target platform is Home Assistant OS
  on Raspberry Pi / aarch64 with Python 3.14.
- VU+ BT/IR remote (Type V), Bluetooth name `VUPLUS-BLE-RCU`.
- A local Bluetooth adapter and the readable Linux input device
  `VUPLUS-BLE-RCU Keyboard`.
- A configured HACS integration if installing through HACS.

The integration requires Linux `evdev`. Home Assistant installs the manifest
requirement `evdev==1.9.3` during setup; no manual `pip` installation is needed.

The Home Assistant process needs read access to devices under `/dev/input`.
Home Assistant OS exposes local evdev devices to the Core integration. With Home
Assistant Container, pass `/dev/input` into the runtime and grant the process read
permissions, typically through the `input` group or a suitable udev rule. Without
access, the device may be missing from the setup dropdown or fail to open.

## Languages

Setup, options, repair dialogs, device names, button names and diagnostic names
are available in German and English. Home Assistant selects translations using
its language settings; names generated by the backend follow the system language.
User-defined names are retained. Changing language does not automatically change
existing entity IDs. The integration entry uses the language-neutral model name
`VUPLUS-BLE-RCU`.

Technical values such as `command`, `action` and `event_type` are identical in
both languages. `command_label` contains the button entity name resolved by Home
Assistant. Use the technical values for filtering and comparisons.

All guides are available in both languages through their language links.

## Installation

### Through HACS

1. In HACS, open the menu at the top right and choose **Custom repositories**.
2. Enter `https://github.com/topic2k/VU-BT-RC` and select **Integration** as the type.
3. Open **VU+ HID Raw Remote** in HACS and download it.
4. Restart Home Assistant.
5. Go to **Settings → Devices & services → Add integration**, search for
   **VU+ HID Raw Remote** and complete [setup](#setup).

Installation as a custom repository requires a public GitHub repository.
Inclusion in the HACS default catalog is not required. See the
[HACS custom repository guide](https://www.hacs.xyz/docs/faq/custom_repositories/).

### Manually

1. Copy the complete `custom_components/vuplus_hid_raw` directory from this
   repository to `/config/custom_components/vuplus_hid_raw`, including its
   `translations` and `brand` subdirectories.
2. Restart Home Assistant and add the integration as described above.

The integration directory must directly contain `manifest.json` and `__init__.py`.
No entry in `configuration.yaml` is required.

## Features

- Configuration through **Settings → Devices & services**.
- Optional remote discovery, pairing, trusting and connection in the config flow.
- Separate confirmation before unpairing after deleting the integration entry.
- Remote selection by Linux device name; the dropdown also shows its current path.
- Home Assistant device registry entry for the remote.
- Diagnostic entities for pairing, connection and reader status.
- A separate event entity for each supported button.
- Button events: `press_start`, `press_end`, `long_press_start`, `long_press_end`
  and `repeat`.
- Automatic reconnection after Bluetooth or evdev disconnection.
- Support for changing `/dev/input/eventX` numbers.

## Device information

The device page displays **VU+ Bluetooth remote**, manufacturer **VU+** and model
`VUPLUS-BLE-RCU`. The software version is the integration version. Linux evdev
does not provide the remote's firmware version, so it is not displayed.

Home Assistant uses the integration icon and logo from
`custom_components/vuplus_hid_raw/brand/`.

## Diagnostic entities

The device page contains five enabled diagnostic binary sensors:

- **Paired**, **Bluetooth connected** and **Trusted** report the corresponding
  states of the associated BlueZ remote.
- **Input device available** indicates whether an evdev device with the
  configured Linux name is currently present.
- **Reading input** indicates whether the evdev reader has opened the device.

Bluetooth states are refreshed on load and every 30 seconds. If the Bluetooth
identity is unknown or BlueZ is unavailable, these three entities are temporarily
unavailable instead of reporting a misleading off state.

## Setup

Add the integration through the UI. Choose **Select an already connected input
device** or **Pair a Bluetooth remote**.

Button detection stores the Linux device name, normally `VUPLUS-BLE-RCU Keyboard`;
it never stores `/dev/input/eventX`. When uniquely identified, the Bluetooth
addresses of the remote and local adapter are also stored for later unpairing.
Keep the remote awake and connected during setup so Linux exposes its evdev
device and it appears in the dropdown.

The default long-press threshold is **500 ms**. Set it during setup or later in
the integration options, from **100 to 5000 ms** in **50 ms** increments.

## Bluetooth pairing

Home Assistant's general Bluetooth setup does not provide a universal Pair/Trust
dialog for HID remotes. This integration supplies an optional pairing flow:

1. Choose **Pair a Bluetooth remote** and put the remote into pairing mode
   according to its manual.
2. Start discovery. It takes about ten seconds and uses powered local Bluetooth
   adapters. Devices named `VUPLUS-BLE-RCU` are offered, optionally with a suffix
   separated by whitespace.
3. Select the remote by its Bluetooth address and adapter. Submitting pairs it
   (`Pair`), marks it trusted (`Trusted = true`) and connects it (`Connect`).
4. Select `VUPLUS-BLE-RCU Keyboard` and the long-press threshold. If Linux has not
   exposed it yet, wake the remote and submit again to refresh the list. An empty
   device list has its own retry dialog.

The flow uses BlueZ over the system D-Bus and does not require `bluetoothctl`.
Home Assistant installs `dbus-fast==5.0.22` from the manifest. HA OS provides BlueZ
and D-Bus access. Container installations also need access to the host's system
D-Bus as well as `/dev/input`. The process needs permission to pair and modify
`Trusted`. Missing adapters, disabled Bluetooth, permission failures and timeouts
produce errors in the dialog and allow another attempt.

Bluetooth proxies cannot be used: the Home Assistant host's Linux system must
expose the HID device locally through evdev. Pairing without PIN entry (Just Works)
is supported. If a PIN or numeric comparison is required, the dialog reports it;
complete that pairing with `bluetoothctl` instead.

Existing pairings are reused. Pairing and trust remain in BlueZ after a later
error or cancellation of setup. Deleting a completed integration entry initially
retains the pairing; removing it requires separate confirmation as described
below. Cancelling stops an ongoing pairing attempt and releases the temporary
pairing agent and discovery sessions owned by this integration.

The integration does not replace the global Bluetooth agent or change adapter
settings. Bluetooth addresses are stored for unpairing; BlueZ device paths,
`hciX` numbers and evdev paths are not stored. The reader searches only by Linux
device name.

## Unpairing after deletion

Deleting the integration entry under **Settings → Devices & services** initially
retains the Bluetooth pairing. A prompt, **Also remove the Bluetooth pairing?**,
then appears under **Settings → System → Repairs**. A custom integration cannot
add a choice to Home Assistant's normal delete dialog, so confirmation is
separate: after deleting the HA entry, but before unpairing.

The prompt offers two choices:

- **Only delete device/integration – keep pairing** (default): closes the prompt
  and retains pairing and trust on the HA host.
- **Also remove the Bluetooth pairing**: only explicitly confirming this choice
  removes the BlueZ device. Connection, pairing and trust are removed from the
  specified adapter.

**Closing or ignoring the prompt, reloading, disabling and restarting do not
unpair the remote.** Pending prompts and their addresses survive HA restarts.
The integration code must remain installed for the prompt to work.

After confirmed removal, pair the remote again before setting it up. Its internal
pairing data is not reset, so it may need to enter pairing mode again. A device
already removed from BlueZ on the original adapter counts as unpaired. If another
or newly created integration entry uses the remote, unpairing is refused.

The pairing assistant records the Bluetooth addresses of the remote and adapter.
For manually paired remotes or entries without this identity, the integration
tries to resolve it uniquely using optional evdev `uniq` and `phys` metadata and
BlueZ devices. This happens during setup, when loading an entry without identity,
and if necessary during deletion. If identity is missing, wake the remote and
reload the integration so it can be saved. Reader discovery and reconnection
continue to use only the Linux device name.

If identity or the original adapter is missing, or confirmed unpairing fails,
the prompt remains open and explains why. The selection resets to **keep pairing**.
There is no automatic retry: another removal attempt needs a new explicit choice
and confirmation. Alternatively, remove the pairing manually with `bluetoothctl`
on the HA host after selecting the correct adapter.

## Events

Each supported button has a separate event entity with device class `button`.
Select the button entity directly in the automation UI. Its event types are
`press_start`, `press_end`, `long_press_start`, `long_press_end` and `repeat`.
Event attributes include `command`, `command_label`, `action`, `key_code`, `value`,
`scan_code`, `usage` and `duration_ms`.

| Home Assistant event type | `action` attribute | Meaning |
| --- | --- | --- |
| `press_start` | `press` | Button pressed |
| `press_end` | `short_release` | Released after a short press |
| `long_press_start` | `long_press` | Long-press threshold reached |
| `long_press_end` | `long_release` | Released after a long press |
| `repeat` | `repeat` | Linux reports a repeated key event |

An event entity's state is the timestamp of its last event. `event_type` contains
that event's type. `duration_ms` is the elapsed press duration in milliseconds.
`scan_code` and `usage` can be `null` if Linux did not provide a scan value.

## Automations

Event entities are the automation interface. Select the desired button entity
using the **Event received** trigger, then choose its event type. No additional
attribute or template filter for the button name is needed.

There are no integration-specific device triggers and no separate bus event.
The event entity is the only automation interface.

### Example: releasing the OK button

This automation creates a persistent Home Assistant notification after a short
press and release of OK. `press_end` means release after a short press.

```yaml
alias: "VU+: OK button released"
triggers:
  - trigger: event.received
    target:
      entity_id: event.vu_bluetooth_remote_ok
    options:
      event_type:
        - press_end
actions:
  - action: persistent_notification.create
    data:
      title: "VU+ remote"
      message: >-
        Button released: {{ trigger.to_state.attributes.command_label }}
mode: single
```

The entity ID can differ depending on the system language during setup and any
custom names. Replace `event.vu_bluetooth_remote_ok` with your **OK** entity ID.

## Short and long presses

Duration is measured with a monotonic clock between `EV_KEY` down and up. An
independent timer emits `long_press` as soon as the threshold is reached; this
does not depend on Linux repeat events. Releasing the button, disconnecting or
unloading the integration cancels the timer.

A short press emits `press` followed by `short_release`. A long press emits
`press`, then `long_press` at the threshold and `long_release` upon release.
Linux repeat events also emit `repeat`, without affecting long-press detection.

The default threshold is **500 ms**. `value` uses Linux evdev's value convention:

```text
0 = release
1 = press
2 = repeat
```

The timer-generated `long_press` contains `value: 1`. `value: 2` exclusively means
repeat. Long presses are determined from actual duration.

## Reconnection

The reader searches by Linux device name. After disconnection it searches again
every two seconds, so changing `/dev/input/eventX` paths are supported.
`MSC_SCAN` is associated only with the next key event and discarded on reconnection.

## Known limitations

- `TV Power` and `AV` do not produce events through the Linux HID/evdev interface
  used here and cannot be automation triggers.
- Bluetooth proxies cannot replace a local evdev device.
- Multiple remotes with identical Linux device names cannot be configured
  separately; device selection and discovery distinguish them only by name.
- Installation through HACS, adding the integration, Bluetooth pairing and
  explicitly confirmed unpairing have been tested with the remote. Automated
  tests still simulate Home Assistant and the BlueZ transport; buttons, long
  presses and reconnection should also be checked on the target hardware before
  a future feature expansion.
